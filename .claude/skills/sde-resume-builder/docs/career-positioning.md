# SDE Career Positioning Framework

## 1. Purpose

This document defines how the candidate's verified experience should be positioned for Software Development Engineer (SDE) applications.

It is a **positioning strategy**, not a source of new candidate facts.

The candidate profile remains the factual source of truth. This document determines:

* Which verified experiences receive emphasis
* How different experiences connect into a coherent SDE story
* Which technical themes should be foregrounded
* Which experiences should be secondary or omitted
* How positioning should adapt to different SDE job descriptions
* Which positioning mistakes must be avoided

---

# 2. Primary Professional Identity

## Target Role

**Software Development Engineer (SDE)**

## Core Identity

**Software Engineer with backend, data-processing, and AI/LLM automation experience.**

The candidate should be presented first as a **software engineer**, not as an AI specialist, data scientist, cloud administrator, or DevOps engineer.

The strongest overall story is:

> Hands-on software engineering experience spanning backend services, data processing pipelines, microservices, API-oriented workflows, incident automation, and AI skill/workflow engineering.

---

# 3. Core Career Narrative

The candidate's experience should form a logical progression:

```text
Backend / Data Processing
        ↓
Microservices & APIs
        ↓
Performance-Oriented Data Pipelines
        ↓
Automation & Tool Orchestration
        ↓
LLM-Powered Incident Workflows
        ↓
AI Skill / Agent Workflow Engineering
        ↓
Software Development Engineer
```

This progression should be visible across the resume without artificially forcing every experience into the same category.

The narrative is:

**The candidate began with hands-on backend and data-processing engineering, developed experience building services and processing pipelines, then moved into incident automation and LLM-powered workflows, and currently applies software-engineering thinking to AI skill and troubleshooting workflow engineering.**

# 17. Keywords From Job Descriptions

Job descriptions should determine **emphasis**, not factual content.

For every JD:

1. Extract required and preferred technologies.
2. Map them against the candidate's verified evidence.
3. Identify exact matches.
4. Identify adjacent/relevant experience.
5. Identify missing technologies.
6. Prioritize verified matches in the resume.
7. Do not add missing technologies merely for ATS matching.

### Example

If a JD requires:

`Python, Docker, Kubernetes, Kafka`

and the candidate has verified:

`Python, Docker`

but not Kubernetes or Kafka:

Use:

**Python, Docker**

Do not add:

**Kubernetes, Kafka**

simply because they appear in the JD.

---

# 18. Missing-Skill Handling

When a target role contains technologies the candidate does not possess, the resume should not attempt to hide the gap through keyword substitution.

Instead:

* Maximize relevant adjacent evidence.
* Use verified transferable engineering concepts.
* Preserve truthful positioning.
* Avoid unsupported claims.

Example:

A distributed-systems JD may mention Kafka.

The candidate's verified experience includes:

* Data pipelines
* Polling
* Asynchronous processing
* Batch ingestion
* Microservices
* Processing state

These can be emphasized as relevant engineering experience.

Kafka itself must not be claimed.

# 20. Metrics Strategy

Metrics should be used when they demonstrate engineering constraints or outcomes.

Currently safe metrics:

* **2+ years** professional experience
* **2–3 GB** data workload
* **~2-minute** processing window

Do not use:

* 100K+ events/day
* Sub-second PostgreSQL latency
* Sub-100ms ML inference
* MTTR reduction
* Percentage performance improvements
* Manual-effort reduction

unless verified later.

A technical constraint can be more valuable than an invented performance percentage.

---

# 21. Bullet-Writing Strategy

Strong bullets should generally follow:

**Action + Engineering Work + Technology/Context + Verified Result/Constraint**

Example structure:

> Redesigned [data-processing workflow] using [verified technologies/techniques] to process [verified workload] within the required [verified window].

Another:

> Built [backend services] using [verified technologies] to [verified engineering function].

Another:

> Engineered [AI troubleshooting workflow] by translating [SOP/procedure] into [skills/tools/input-output workflow] and testing against incidents.

Bullets should demonstrate engineering decisions rather than simply list responsibilities.

---

# 22. Evidence Hierarchy

When choosing between possible resume statements, prefer evidence in this order:

1. Verified engineering outcome
2. Verified engineering decision/problem solved
3. Verified implementation
4. Verified technology usage
5. General responsibility
6. Generic skill claim

Example:

Prefer:

> Redesigned data processing to eliminate intermediate CSV disk I/O and meet the ~2-minute processing window.

Over:

> Worked on data processing using Python.

The first communicates engineering judgment and outcome.

---

# 23. Omission Strategy

The goal is not to list everything the candidate has encountered.

The goal is to present the strongest truthful SDE evidence.
